# 签署记录

本目录是 **CLA 签署的登记簿**，不是签署用的收件箱。

**只有维护者会往这里写文件。** 贡献者不提交本目录的任何内容——原因见下，这不是流程洁癖。

## 为什么签署记录不能由贡献者自己提交

两个独立的理由，任一成立就够：

1. **技术在先**：`cla` 检查读的是**基线分支**的 `signatures/`。如果签署记录要靠一个 PR 提交进来，那个 PR 本身就会因为「找不到签署记录」而永远无法合并——自锁。
2. **法律在后**：一份由贡献者自己在 PR 里写的声明文件，是他**对自己的陈述**，不是签署件。真到了需要主张权利的时候，它的证明力和「我在邮件里回复同意」差着量级。

所以正确的顺序是：**人先签，记录后落。**

## 目录结构

```
signatures/
├── README.md                    本文件
├── icla/
│   ├── TEMPLATE.md              记录格式（只给维护者看，不用改）
│   └── <github-login>.md        个人签署记录
└── ccla/
    ├── TEMPLATE.md              公司签署记录格式
    ├── <company-slug>.md        公司签署记录（含覆盖名单指向）
    └── covered/
        ├── TEMPLATE.md
        └── <github-login>.md    被该公司 CCLA 覆盖的开发者，一人一个文件
```

**文件名规则**：`<github-login>.md`，一律**小写**。GitHub 登录名本身不区分大小写，机器人和人可能写出不同的大小写，统一小写可以让「找不到记录」这类假红彻底消失。

## 签署怎么发生（贡献者视角）

1. 阅读 [`CLAs/ICLA.md`](../CLAs/ICLA.md)（个人）或 [`CLAs/CCLA.md`](../CLAs/CCLA.md)（代表公司）。
2. 打印、手写签名、扫描；或使用你所在公司认可的电子签方式。
3. 把签署件的扫描件/PDF **发到 `admin@sji.xin`**，邮件正文写明你的 GitHub 登录名（代表公司的还要写公司名与授权人职务）。
4. 维护者核对后把记录提交进本目录并告诉你一声。**你的 PR 下一轮检查就会自动通过**，不需要你做任何事。

签署件原件不进公开仓库——那里会长期挂在搜索引擎里，不该有你的手写签名。仓库里只放登记信息。

## 内部员工

中国法下计算机软件职务作品的著作权归单位（《著作权法》第 18 条、《计算机软件保护条例》第 13 条），员工为完成本职工作写的代码本来就属于公司，**不需要签 ICLA**。

但仍建议每位员工留一条记录：姓名 + GitHub 登录名 + 公司邮箱 + 岗位。目的不是取得授权，而是把「这个提交是职务作品」这件事从「翻一堆劳动合同和岗位说明书」降到「翻一页纸」。融资、被收购、软著登记、诉讼，尽调都会查这条链。

同时请确认劳动合同或单独的《知识产权归属确认书》覆盖了这项工作——这一步在仓库之外完成，仓库不承担。

离职时记得三件事：签权利确认 → 从 `signatures/` 里移除或标注失效 → 撤销仓库权限。第三件最容易忘。

## 协议版本与重新签署

每份记录都带 `CLA-Version:` 字段，机器人会校验它与当前版本一致。条款发生实质变化时把版本号 +1，所有记录随之失效，需要重新签署——这是有意的：一份旧条款下的授权，不能覆盖新条款才引入的权利。

不要为了「让 CI 变绿」去改这个字段。要改的是签署，不是字符串。
